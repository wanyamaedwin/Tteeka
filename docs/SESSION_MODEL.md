# Session Model

## Purpose and boundary

B1.4 establishes persistence and cryptographic primitives for opaque server-side sessions. A Session is dependent security data belonging to one global User. PostgreSQL is authoritative for existence, expiry, revocation, and metadata. B1.4 does not issue or consume sessions through HTTP and implements no login, logout, cookie, middleware, guard, renewal, rotation, or cleanup workflow.

## Opaque architecture and User scope

The client-side token is a meaningless random identifier. It contains no User, Merchant, Membership, Role, Permission, timestamp, contact detail, or signed JSON payload. It is not a JWT.

A User may have many Sessions, and every Session belongs to exactly one User. Session has no `merchantId`: authentication establishes global human identity, while future Merchant authorization continues through `User -> MerchantMembership -> MembershipRole -> Role -> Permission`. One authenticated User can work across multiple Merchants without freezing a Merchant into authentication persistence.

## Data model

| Prisma field | PostgreSQL column | Contract                                               |
| ------------ | ----------------- | ------------------------------------------------------ |
| `id`         | `id`              | UUID primary key generated by PostgreSQL 18 `uuidv7()` |
| `userId`     | `user_id`         | Required UUID foreign key to `users.id`                |
| `tokenHash`  | `token_hash`      | Unique lowercase SHA-256 hex digest, `char(64)`        |
| `createdAt`  | `created_at`      | `timestamptz(3)`, default current time                 |
| `lastUsedAt` | `last_used_at`    | `timestamptz(3)`, default current time                 |
| `expiresAt`  | `expires_at`      | Required `timestamptz(3)` with no database default     |
| `revokedAt`  | `revoked_at`      | Nullable `timestamptz(3)`, default null                |
| `userAgent`  | `user_agent`      | Optional diagnostic text, `varchar(512)`               |
| `ipAddress`  | `ip_address`      | Optional IPv4/IPv6 text, `varchar(45)`                 |

`expiresAt` is deliberately supplied by a future issuance layer; B1.4 defines no TTL or sliding-expiry policy. A non-null `revokedAt` is the revocation fact. `lastUsedAt` records the most recent successful future authentication use, but B1.4 performs no automatic updates. Explicit timestamps make lifecycle derivable, so there is no duplicated `SessionStatus` enum or generic `updatedAt`.

Expired and revoked rows remain stored as security/session history until a future explicit retention policy removes them. They are not automatically deleted.

## Token generation and storage

`@tteeka/security` uses Node's cryptographic random source to generate 32 bytes, providing 256 random bits, and encodes them as unpadded base64url (normally 43 characters). `createSessionToken()` returns the secret raw `token` and its `tokenHash`; `hashSessionToken(token)` provides the same deterministic lookup digest for future incoming-token processing.

The raw token must be returned to a future client exactly once and must never be stored or logged. PostgreSQL stores only its lowercase hexadecimal SHA-256 digest. `sessions_token_hash_key` makes hashes globally unique and supplies the future indexed authentication lookup.

SHA-256 is deliberately deterministic and unsalted here. Session tokens are high-entropy machine-generated secrets, not low-entropy human passwords. Determinism allows a future incoming raw token to be hashed and looked up efficiently by the unique index. Argon2, bcrypt, a salt column, and a pepper are therefore not part of B1.4; password hashing remains separate.

## Relations, indexes, metadata, and privacy

`sessions_user_id_fkey` uses `ON DELETE CASCADE` and `ON UPDATE CASCADE`. Sessions are ephemeral dependent security material and must not outlive a legitimately deleted User. The restrictive MerchantMembership FK still prevents deletion of a referenced User, preserving both User and Sessions.

`sessions_user_id_revoked_at_expires_at_idx` supports future active-session listing, revoke-all, and administration by User. The unique token-hash constraint already creates its own index, so there is no redundant token index.

User-Agent and IP address are optional security/diagnostic metadata only. They are not authentication factors: no device fingerprinting, IP pinning, or rejection on IP change exists. Collection should be minimized, exposure limited, and retention governed by a future privacy policy.

## Authority and future work

PostgreSQL—not Redis—is Session authority. Redis Session storage and caching are absent so revocation and expiry facts have one durable source of truth.

Future reviewed checkpoints may implement password verification followed by Session issuance, secure cookie transport, request authentication, logout/revocation, logout-all, Session listing, rotation, renewal, retention cleanup, and privacy policy. None is implemented in B1.4. Cookie attributes such as HttpOnly, Secure, and SameSite require their own issuance design; there are currently no cookies, JWTs, refresh tokens, bearer tokens, authentication guards, controllers, repositories, or Session services.
