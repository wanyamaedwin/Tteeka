# Password Credentials

## Purpose and boundary

B1.2 provides Tteeka's password credential storage and cryptographic foundation. It can hash a plaintext password, verify a candidate against an encoded hash, detect hashes that need upgrading, and store one password credential for a User. It does not authenticate a request or expose any login, registration, password-change, or password-reset API.

`PasswordCredential` is separate from `User`. User remains the global human identity established in B1.1, while PasswordCredential represents one authentication mechanism attached to that identity. This separation allows future mechanisms such as OTP, passkeys, or federated identity to be designed without placing every authentication concern on User. Those mechanisms are not implemented.

## Data model

A User may have zero or one PasswordCredential. A PasswordCredential belongs to exactly one User. The database-enforced unique `user_id` index makes this a true optional one-to-one relationship.

| Prisma field        | PostgreSQL column     | Contract                                             |
| ------------------- | --------------------- | ---------------------------------------------------- |
| `id`                | `id`                  | UUID primary key, generated by PostgreSQL `uuidv7()` |
| `userId`            | `user_id`             | Required and unique UUID foreign key to `users.id`   |
| `passwordHash`      | `password_hash`       | Required Argon2 PHC string, `varchar(512)`           |
| `passwordChangedAt` | `password_changed_at` | `timestamptz(3)`, default current time               |
| `createdAt`         | `created_at`          | `timestamptz(3)`, default current time               |
| `updatedAt`         | `updated_at`          | `timestamptz(3)`, maintained by Prisma               |

`passwordChangedAt` records when the currently stored credential was established or last changed. A future password-change service must update the hash and this timestamp together. Future session-security logic may use the timestamp, but B1.2 has no sessions or invalidation behavior.

PasswordCredential is dependent security material. Its foreign key uses `ON DELETE CASCADE`, so a legitimately deleted User cannot leave credential material orphaned. This is an explicit exception to the restrictive deletion policy for identity/history relationships. A User with a MerchantMembership still cannot be deleted because the B1.1 membership foreign key remains `ON DELETE RESTRICT`.

## Argon2id

Password cryptography lives in `@tteeka/security`, independent of Prisma, PostgreSQL, NestJS, the API, and worker. The package uses Argon2id with explicit Tteeka parameters:

- memory cost: 19,456 KiB
- time cost: 2 iterations
- parallelism: 1
- hash length: 32 bytes

The settings are centralized so upgrades do not depend silently on future dependency defaults. `hashPassword` lets the Argon2 implementation generate a fresh cryptographically secure random salt for every hash. Salts are never static, reused, or derived from user data.

The database stores only the encoded PHC string. That string contains the algorithm identifier, version, salt, Argon2 parameters, and resulting hash needed for verification. Tteeka does not duplicate the salt, memory cost, time cost, or parallelism into separate columns, and it does not encrypt passwords.

## Security API

- `hashPassword(password)` returns an Argon2id PHC string using the centralized configuration. It does not log or persist either input or output.
- `verifyPassword(password, encodedHash)` returns `true` for a match and `false` for an incorrect password or malformed/corrupted encoded hash. It does not expose raw dependency errors.
- `passwordNeedsRehash(encodedHash)` returns whether the stored hash differs from Tteeka's current Argon2 parameter baseline. Malformed hashes return `true`. It does not update storage.

Plaintext passwords may exist only transiently at a future credential-creation, change, or login boundary. They must never be written to database columns, logs, fixtures, exception messages, analytics, or queues. Complete encoded hashes and salts must also not be logged.

## Intentional omissions and future direction

B1.2 introduces no password pepper. A pepper may be evaluated later as defense-in-depth only after secret storage, access, rotation, and incident procedures are designed.

The hashing package deliberately contains no password-strength policy. Length rules, breached-password checks, and other credential-acceptance policy belong to a future application service, not the cryptographic primitive. Uppercase, number, symbol, password-history, and similar rules are not implemented.

The following directions are explicitly future work and are not implemented:

- A login flow may locate a User, retrieve the credential, verify the candidate, and replace the hash after a successful verification when `passwordNeedsRehash` is true.
- A password-change flow may verify the existing credential where appropriate, hash the replacement, and atomically update `passwordHash` and `passwordChangedAt`.
- A password-reset flow requires separately designed reset tokens, expiry, abuse controls, delivery, and session consequences.
- Registration, sessions, cookies, JWTs, refresh tokens, OTP, invitations, account lockout, rate limiting, roles, permissions, and authentication/authorization controllers remain absent.

Applications may depend on both `@tteeka/security` and `@tteeka/database`. `@tteeka/security` must not depend on the database package. `@tteeka/database` has no runtime security dependency; its integration tests use `@tteeka/security` only as a development dependency to prove that an encoded hash—not plaintext—crosses the persistence boundary.
